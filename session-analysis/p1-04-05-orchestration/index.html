Correction circuit breakers did not hold

Six subagent threads exceeded four total turns, and one C2 correction writer reached nine. A C3 architecture thread reached eight turns. The policy allows an initial writer turn plus at most three corrections and requires release on a material role change or exhausted circuit. Regardless of labels, these long-lived threads defeated the bounded-context intent and correlate with repeated re-freezes and reviewer churn.

The metadata research question should not have stalled C2

The root asked permission for bounded, read-only metadata/API research at 07:33 UTC on 8 September. The owner answered at 15:50 UTC: an 8 hour 17 minute gate span. Research then took about 41 minutes and surfaced the genuine design decision; the owner resolved that second question 16 minutes later.

The classification was wrong. Read-only endpoint/schema research was already within ordinary task scope and did not authorize a DuckDB download, mutation, persistence, or activation. The root should have researched first and asked only the actual metadata-authority choice. The entire span cannot be called saved critical path because the owner may have been unavailable, but useful work was unnecessarily forbidden; under the observed response opportunity, the genuine decision could plausibly have been ready roughly 57 minutes earlier.

Heavy leases: make them weighted, not simply plural

The run supports a more generous policy only in bounded form. One restore/test family began with 2.28 GiB available and bottomed at 1.46 GiB without OOM or severe paging. Another snapshot had roughly 3 GiB available, so two similarly bounded operations could have remained above the 1.0 GiB floor. But a default parallel MSBuild attempt expanded from 30 to 90 heavy processes and ended with only 1.53 GiB available plus a non-diagnostic failure.

The evidence does not justify two unrestricted solution builds. It supports weighted reservations: retain one lease for restore or default-parallel full builds; allow two only for serial/single-node or targeted test operations whose measured reservations leave the hard floor and warning margin intact. This run recorded no causal heavy-lease queue delay, so throughput benefit remains unproven.

The root then had to determine which prior slice owned each failure so it would not send the fix to the latest, innocent Core writer.

Required workflow correction

Every writer should compile the changed project when admitted. If a heavy lease is unavailable, label the handoff “static-only” and stop cumulative review/integration at a mandatory project-build gate. After merging path-disjoint slices, run one serial cumulative build before more semantic review. A final reviewer must reject any acceptance packet without exact build evidence.

PR timing and worktree cleanup were both too late

Publication

P1-05’s dormant closeout was pushed directly to main because the frozen topology allowed it. By the time the owner requested PR visibility, a retroactive PR had no diff. P1-04’s draft topology was accepted only near the stop boundary; PR #111 was created at 19:18 UTC, eleven minutes after the pause request.

Worktrees

The audit found 29 registered worktrees. Fresh ownership and “park, do not silently delete” explain the accumulation, but release conditions were not acted on. One PR worktree was added, 27 obsolete worktrees were safely removed with branches retained, 11.11 GiB was freed, and three remained.

Long milestones should get draft PRs at their first coherent reviewed checkpoint, while acceptance and merge remain separate gates. Clean, unowned worktrees should be retired at every accepted, rejected, or correction-exhausted milestone after preserving the branch/tip. Safety explains why deletion was not automatic; it does not justify delaying proof-and-remove until the owner notices disk use.

Recovery was safe, but expensive

The run survived usage-limit interruptions and a Windows reboot, preserved exact branch/tip state, and stopped with a sealed capsule. Thirteen compactions align with thirteen recovery-snapshot command occurrences, and maximum observed root input was 214,193 tokens—below the 272k premium-pricing threshold. That is good durability evidence.

There is no matched baseline proving that hot recovery reduced work. The transcript also shows a checksum mismatch that triggered cold repair and independent review. Pattern-derived root counts found 241 capsule-hook occurrences, 246 recovery-manifest builder occurrences, 128 resource snapshots, and 587 nested patch calls. Some were legitimate barriers, but the scale indicates that recovery/state machinery became a first-class workload.

Astra allocation was compliant; stability was mixed

All five explicit GPT-6 Astra spawns were architecture/reconciliation leads, not mechanical status work. Separate Sol/xhigh specification reviews followed. That satisfies the model-role boundary. Downstream stability was weaker: C2 and C3 each needed further architecture or seam re-freezes, and the longest C3 architecture thread ran eight turns.

Recommended changes, in priority order

  1. Install compile gates between integration waves. Use targeted project builds per writer and one serial cumulative build after integration.
  2. Enforce correction limits mechanically. Release at the fourth writer turn or on material role change.
  3. Make long waits the default. Use 300–600 second event-driven waits and no-change-silent commentary.
  4. Create draft PRs early. Freeze base/head and create a WIP PR at the first coherent milestone.
  5. Retire worktrees at lifecycle boundaries. Preserve branches, but remove clean, unowned worktrees promptly.
  6. Replace the global heavy mutex with weighted admission. Permit two bounded operations only when measured reservations preserve the floor.
  7. Stop asking permission for read-only diagnosis. Ask only for genuine authority or outcome decisions.
  8. Reduce capsule churn. Audit the 241 hook and 246 manifest-builder occurrences and coalesce unchanged-state work.
